## 專案背景（Market Problem）

工業 B2B 官網常見的失敗模式，不是「沒有網站」，是網站停在「公司介紹＋
一個聯絡表單」的階段：內容以公司想說的話為中心，而不是以買主決策路徑
為中心；產品規格散落在 PDF 或業務口頭說明中，訪客無法自行比較；中英文
版本品質落差大，英文版經常是機器翻譯或逐字直譯；詢價流程只有一句
「請聯絡我們」，業務團隊收到的第一封信往往缺乏足夠資訊，還要再來回
確認一輪才能開始評估。

這個概念案例示範的是：把「工業採購決策」的實際步驟——確認能力範圍、
比較產品規格、確認適用產業、遞交結構化需求——直接做進網站的資訊架構，
而不是把這些步驟留給業務團隊事後補救。

## 目標客群

三種真實存在的 B2B 工業採購路徑，而非單一「訪客」假設：

1. **海外採購人員／工廠管理者**——透過搜尋、展覽名單或業務開發信進站，
   需要在幾分鐘內確認「這家供應商的能力範圍是否對得上我的產業與問題」。
2. **自動化／製程工程師**——經常是被轉發連結進站，需要的是規格表、
   系統相容關係與適用情境，而不是行銷語言。
3. **企業決策者**——通常最後才進站確認，需要理解定位與合作流程，
   才會核准下一步。

首頁因此提供「依角色選擇瀏覽路徑」的雙入口設計（產業應用 vs. 產品
規格），而非要求所有訪客走同一條路徑。

## 資訊架構

十個頁面群組、雙語（zh-TW／en）平行路由：首頁、解決方案（總覽＋6 個
方案，其中 1 個完整深度詳細頁）、產品（總覽＋3 個產品皆有完整規格
頁＋選型比較表）、產業應用（總覽＋4 個產業，其中 1 個完整深度詳細
頁）、關於我們、技術資源（2 篇實用文章）、聯絡與 RFQ、隱私權說明、
404。結構化內容（產品、方案、產業）以 Astro Content Collections 管理
並以 Zod Schema 驗證，確保跨頁引用（相關產品、相容方案）不會產生
內容漂移。

## 使用者路徑與轉換策略

雙層 CTA：「提交專案需求」（`?intent=project`）導向完整 RFQ 流程；
「索取技術建議」（`?intent=technical-advice`）給尚未準備好完整需求的
訪客一個較低承諾的入口——進入聯絡頁後，開場文案與表單預選會依 Query
Param 自動調整，而非兩個 CTA 導向同一份無差異表單。

RFQ 表單收集公司、職稱、產業、專案類型、預算區間、時程、是否已有規格、
是否需要保密協議等欄位，讓業務與工程團隊在第一次聯繫前就能做初步篩選。
表單同時實作 Demo Mode／Live Mode 雙軌：Demo Mode 下完整執行前端驗證，
但明確告知「這示範完整 RFQ 驗證體驗，資料不會被送出或儲存，沒有實際
回覆承諾」，避免作品集展示產生「已送出成功」的誤導性假象——這是我們
在自己的作品集上也堅持的誠信原則，不因為是 Demo 就放寬標準。

## 視覺方向

視覺定位「精密是可以被看見的過程，而不是需要被相信的宣稱」：以工程圖紙
的秩序感（網格、留白紀律、資料化的規格表）取代常見的科技新創漸層或
制式工業感樣板。色彩策略採用 Restrained（深海軍藍灰 `#12181f` ＋暖白
`#f7f5f1` ＋單一銅橘強調色），刻意避開 AI 生成介面常見的紫藍漸層與
過度玻璃擬態。完整決策記錄於 `DESIGN.md`。

## 技術決策

Astro＋TypeScript Strict 靜態生成，零前端框架（原生 JavaScript 處理
互動：行動選單、FAQ Accordion、表單驗證、語言切換、分析事件橋接），
CSS Custom Properties 管理 Design Token，Content Collections 管理
結構化內容。技術選型完整記錄於 `docs/PROJECT_BRIEF.md`。

## 雙語處理

檔案系統路由分流（`/zh-tw/`、`/en/`），共用型別化字典（`DeepString<T>`
工具型別確保英文字典鍵值結構與中文同步，翻譯缺漏會在 TypeScript 編譯期
報錯，不會等到執行期才被發現）。英文文案依英文語感重新組織句子結構，
非逐字直譯。

## SEO

每頁獨立 Meta Title／Description、Canonical、hreflang（zh-Hant-TW／
en／x-default）、Open Graph、語意化 HTML、Breadcrumb、動態 Sitemap／
Robots.txt，結構化資料僅在內容真正符合時輸出（例如 FAQPage 僅用於
真正有 FAQ 內容的頁面；Product Schema 明確不輸出價格與評價欄位，
避免虛構 Demo 內容被搜尋引擎誤判為真實可購買商品）。

## 無障礙

Skip Link、可見 Focus 狀態、表單錯誤 ARIA 關聯（含 Radio Group 與
Checkbox 的錯誤路徑）、鍵盤可完整操作的導覽與表單、Mobile Nav 完整
Focus Trap 與背景 Inert 處理、`prefers-reduced-motion` 支援。這些不是
事後補上的檢查清單，過程中透過 axe-core 自動化掃描找出並修正了
2 個真實的無障礙缺陷（見下方「QA 證據」）。

## QA 證據（真實可重現的數字）

- **Playwright 端到端測試**：198 個測試全數通過，涵蓋 7 種必要
  Viewport（360／390／768／1024／1280／1440／1920px）× 14 種頁面
  類型的無橫向溢位檢查、Mobile Nav 完整互動流程、RFQ 表單驗證（含
  Select／Radio Group／Checkbox 錯誤路徑）、404、Console Error 檢查、
  PDF 下載連結有效性、語言切換、FAQ Accordion、`prefers-reduced-motion`。
- **無障礙掃描**：axe-core 於全部 14 種頁面類型＋Mobile Nav 開啟狀態
  執行，**0 個 Critical、0 個 Serious 違規**。過程中實際發現並修正
  2 個真實缺陷：Mobile Nav 背景在選單開啟時並非真正 Inert（CSS
  Containing Block 問題）、Footer Logo 英文字重在深色背景對比不足
  （2.97:1，未達 WCAG AA 4.5:1）。
- **Lighthouse**：5 個必要頁面（中文首頁桌面／手機、英文首頁手機、
  產品詳細頁、聯絡頁）Performance／Accessibility／Best Practices
  皆為 **100 分**。SEO 分數在 Demo Mode 下為 66 分，唯一失分項目是
  `is-crawlable`（因刻意的 `noindex` 索引安全機制），已透過切換至
  Production Mode 重新測試驗證：關閉 Demo Mode 後 SEO 立即恢復 100 分，
  證明 66 分是設計行為而非缺陷。
- **內部連結檢查**：50 個頁面、1951 個內部連結，0 個失效連結。
- **色彩對比**：`docs/CONTRAST_AUDIT.md` 記錄每個主要 Token 的計算
  過程，Accent／Muted 相關 Token 從實測 3.13–3.95:1（未達標）調整至
  4.74–5.53:1（一般文字）或 3.46:1 以上（UI 邊界），同時保留品牌
  銅橘色相家族。

## 不得編造的成效項目（案例頁撰寫時務必遵守）

依指令與本專案一貫原則，正式案例頁**不得**加入以下任何一種內容：

- 任何形式的流量、轉換率、營收或業績提升百分比（因為沒有真實客戶）
- 客戶推薦、客戶 Logo 牆、客戶滿意度分數
- 「業界領先」「唯一」「最」等排他性或排名宣稱
- 任何認證、獎項或合規標章（本案例明確聲明不含此類內容）

可以呈現的是：技術執行的真實數字（測試通過數、掃描結果、Lighthouse
分數）、可公開瀏覽的 Demo 連結、螢幕截圖、資訊架構圖、Design Token。
